# Участник 1: реализация и проверка интеграции

Дата проверки: 23 сентября 2026. Код расположен в `src/TwinTurbo.ai/` с логическим
именем пакета `windoracle`. Переименование команды сохранено через `package-dir`.
README описывает более широкий план; подтверждённые команды этого слоя приведены ниже.

## Что работает

- Аудит CSV без привязки к календарному периоду; импорт с явной семантикой времени.
- Почасовая сетка с n_samples/coverage/quality_flag. Неполные и отсутствующие часы
  имеют null-цель; пропуски не заполняются нулём или будущими значениями.
- SQLite: неизменяемые версии наблюдений, моделей, bias, прогнозов, журнал решений.
- Снимок as-of, временные ограничения модели и bias, проверка ровно 48 строк на турбину.
- NOAA GFS 0.25°: ограниченные Range-запросы, GRIB-декодирование, сырой кэш, SHA-256,
  выбор допустимого выпуска и ограниченный fallback к более старому выпуску.
- VirtualClock, последовательный replay, пересчёт при новом цикле GFS, идемпотентность.
- Единый ForecastService для CLI/UI, сравнение выпусков, CSV, переносимые JSON с checksum.
- Чтение результатов интерфейсом доступно без загруженной модели.

Математическая модель, обучение, оценка качества и UI принадлежат участникам 2 и 3.
Тестовая модель в prepare_demo.py явно синтетическая; она не является их заменой.

## Реальная погода: критическая зависимость подтверждена

Источник: [NOAA GFS на AWS](https://registry.opendata.aws/noaa-gfs-bdp-pds/),
публичный operational-архив без аккаунта. Проверено полное скачивание и декодирование
полей двух циклов: 2026-01-15 12:00 UTC и 2026-02-01 12:00 UTC.
В каждом получены необходимые 96 точек (2 турбины × 48 часов); кэш содержит 104 точки,
включая запас для интерполяции и границ интервалов. Даты проверки — примеры, не ограничения кода.

| Выпуск | SHA-256 списка исходных фрагментов |
| --- | --- |
| 2026-01-15 12 UTC | 5b159c017eda1e86375806f63f25a9c626a43536c1faa11915312090df8cea5c |
| 2026-02-01 12 UTC | b93ac47275619c6ac1b24ca0b9f400a34d42a81d8fe43d07cf15e5360c5b1bc5 |

Полный manifest сохраняет URL, диапазоны байтов, хеши отдельных фрагментов,
Last-Modified, исходный цикл, уровень ветра, метод интерполяции и время скачивания.
Пример файла: `https://noaa-gfs-bdp-pds.s3.amazonaws.com/gfs.20260115/12/atmos/gfs.t12z.pgrb2.0p25.f006`.
Скачиваются U/V ветра на 100 м и температура на 2 м каждые 3 часа.
Почасовые u/v и температура интерполируются внутри одного выпуска; скорость — hypot(u,v).
Это прогнозные значения на временных отметках, а не гарантированное часовое среднее.
Для 1-часовых исходных полей можно настроить sample_step_hours: 1 и увеличить лимит при необходимости.

`available_at = max(Last-Modified всех нужных GRIB-файлов, run_init_time + 6 часов)`.
Шесть часов — явное консервативное допущение, настраиваемое в YAML.
Last-Modified является свидетельством времени объекта архива, не доказательством
точного времени исходной публикации NOAA. Если объект обновили позже origin, выпуск
отклоняется, а не задним числом объявляется доступным.

Координаты извлечены из перенаправлений ссылок официального ТЗ:

- [Турбина 1](https://maps.app.goo.gl/iN6svMt69D5qRpFU9): 43.645150, 78.535604.
- [Турбина 2](https://maps.app.goo.gl/8UQMwsYavY6nLvFY8): 43.643198, 78.538828.

Обе попали в одну ближайшую ячейку (43.75, 78.5); это ожидаемое ограничение сетки
GFS. Отдельные локальные ветровые условия моделью сетки не разрешаются.
100 м — выбранный уровень погодного признака, не утверждение о высоте турбины.

## Работа по предоставленным данным

По указанию пользователя код не фиксирует месяц или местность. Импорт принимает
полный диапазон CSV, replay получает даты или использует последний день импортированной
истории как одиночный пример. Координаты и timezone настраиваются.
В example YAML: UTC, interval_start, задержка 15 минут, time_basis: assumed.
Это техническое допущение для обработки; фактический пояс SCADA неизвестен.
Предупреждение сохраняется в каждом прогнозе. Его необходимо подтвердить перед
заявлением точности совмещения с погодой. Начало/конец интервала можно переключить.
При instant часовое среднее является оценкой из отсчётов, не измеренной энергией.

Импорт реальных файлов проверен: 142360 и 149499 исходных строк, по 25392 часовых
слота. Полных часов: 23667 и 24785; частичных: 96 и 219; отсутствующих: 1629 и 388.
Пустые ячейки и повторы в исходниках не обнаружены. Номиналы неизвестны, поэтому
выходная единица — normalized_power. Данные не переводятся в MW/MWh.
CSV и ~100 МБ локального погодного кэша не включаются в Git.

## Проверенные команды

Из корня репозитория, Python 3.12 (проверенная среда):

```sh
python -m venv .venv
# Windows: .venv\Scripts\Activate.ps1; Linux/macOS: source .venv/bin/activate
python -m pip install -r requirements.lock
python -m pip install --no-deps -e .
python -m pytest -q
python -m windoracle --help
python -m windoracle doctor
```

requirements.lock — проверенный набор Windows. На других ОС GRIB может потребовать
платформенные зависимости ecCodes; численные результаты там ещё не проверены.

```sh
python -m windoracle audit-csv data/raw/turbine_1.csv data/raw/turbine_2.csv
python -m windoracle ingest --turbine-1 data/raw/turbine_1.csv --turbine-2 data/raw/turbine_2.csv
python -m windoracle weather fetch --origin 2026-01-15T18:00:00Z --run 2026-01-15T12:00:00Z
python -m windoracle weather fetch --origin 2026-02-01T18:00:00Z --run 2026-02-01T12:00:00Z
python -m windoracle weather audit --origin 2026-01-15T18:00:00Z
```

CSV-пути заменить фактическими. YAML по умолчанию configs/site.example.yaml;
для собственной конфигурации у каждой команды есть --config. Для bulk weather fetch
--start/--end — целевые даты включительно, --max-runs явно разрешает нужное число
origin. По умолчанию не более двух; лимит байтов применяется отдельно к каждому run.
Без --run выбирается последний подходящий цикл, при отказе проверяются более старые.

Проверка сквозной интеграции без чужой модели:

```sh
python scripts/prepare_demo.py --fixture --origin 2025-06-01T18:00:00Z
python -m windoracle verify --input outputs/integration-smoke
python -m windoracle export --input outputs/integration-smoke --allow-fixture --output outputs/smoke.csv
python scripts/prepare_demo.py --fixture --real-weather --origin 2026-02-01T18:00:00Z --output outputs/archive-smoke
```

Первый сценарий сохраняет 3 версии, 288 строк; второй — 96 строк с настоящей погодой
и явно тестовой моделью. Strict-экспорт обоих сценариев запрещён.
Файлы outputs можно перенести на другую машину и проверить без исходной базы.

После появления фабрики участника 2:

```sh
python -m windoracle predict --origin 2026-01-15T18:00:00Z --predictor windoracle.models.registry:load_predictor
python -m windoracle replay --start 2026-01-15 --end 2026-01-15 --updates --predictor windoracle.models.registry:load_predictor
```

Эти две команды требуют ещё не предоставленной модели; её фабрика должна вернуть
ModelState и predict(snapshot, bias=None), см. CONTRACTS.md. Сервис не обучает модель
втайне. Команды evaluate/train и параметры --fit-before-first-origin/--adaptation
из старой спецификации README в слое 1 не реализованы, это дальнейшая интеграция с участником 2.

## Совместная работа

GitHub Actions (`.github/workflows/ci.yml`) запускает установку обычного пакета,
все тесты команды и offline smoke на Windows/Linux при push/PR. Проверка не
требует CSV, секретов или скачивания погоды. Итог конкретного запуска виден в Actions.

Загрузка погоды возобновляется через content-addressed кэш запросов: URL + диапазон
байтов привязаны к SHA-256 и исходным заголовкам. Прерванный запуск повторно использует
завершённые фрагменты, проверив хеши; незавершённый фрагмент скачивается заново.
Ошибки целостности не скрываются. Этот кэш фиксирует полученную версию архива,
не обновляет старые ответы молча.
`weather fetch --max-download-mb 500 --progress ...` ограничивает сетевые данные
всей команды, включая fallback, и выводит прогресс в stderr. Попадания в кэш бюджет
не расходуют. Отдельный лимит размера run в YAML продолжает действовать.
При исчерпании бюджета команда останавливается, оставляя проверенные фрагменты
для продолжения. Сводка transfer в отчёте относится ко всей команде.

Сохранены владение файлами и существующее переименование. Перед финальным push
участник 1 получает свежий origin/main, проверяет изменения, объединяет их обычным
merge и повторяет проверки. Force-push не применяется. Проверка совместимости
относится к полученному состоянию main; будущие коммиты потребуют следующего прогона.
